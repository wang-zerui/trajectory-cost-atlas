The idea under test

被检验的具体想法

先把想法拆成两半——哪半是老生常谈、哪半可能是新的。

① turn 级换模型(已成熟)

agent loop 里每个 turn 从模型池选强/弱模型。这部分被大量工作覆盖(见下方 Tier 1/2),不新。

② 用 decode↔cache-write 价差当路由信号(空白)

把「本 turn 预测 decode 量 × $25」和「之后强模型重吸收该输出的 cache-write × $6.25」直接放进路由目标函数。目前没有论文把它当正向套利信号。

弱模型生成 + 灌入强模型 ≈ $11.25 / 1M
强模型直接 decode = $25 / 1M

1M output tokens:Haiku 生成 ($5) + Opus cache-write 吸收 ($6.25) ≈ $11.25 · vs Opus 直接 decode $25 —— 结构性套利 ~55%(前提:弱输出够好 + 强模型缓存未过期)。定价来自 Anthropic prompt-caching 官方页。

Verdict

结论:部分覆盖

◆ turn 级 strong/weak 路由本身——已成熟

MTRouter、TwinRouterBench、TRIM、STEER、Router-R1 都在做 turn/step 级选模型。"按 turn 换模型"不是新贡献。

◆ decode-cost-aware + cache-state-aware 的路由策略——空白

这些工作大多优化 FLOPs/token 或按难度路由;唯一碰到 prompt cache 的是 MTRouter,却把缓存丢失当成"缺点要规避",而不是把 decode-vs-write 的价差当成要利用的套利信号。没有一篇把"预测 decode 量 × 单价差"作为正向路由目标。

→ 这就是你想法里真正没被占的那一格。

Tier 1 · closest

Agent loop 里的 turn 级路由

最贴近你想法的一类:在面向环境的多轮 agent 里,每个 turn 选模型。

MTRouter — Cost-Aware Multi-Turn LLM Routing

Yiqun Zhang et al. · ACL 2026 Main · arXiv 2604.23530
最相关
背景

长程多轮任务需要大量顺序模型调用,推理成本累积。现有 router 多按整条 query 路由,没有 turn 粒度。

Motivation

在固定成本预算下,每个 turn 从模型池选最合适的模型——不同 turn 难度差异大,应差异化分配。

方法

把交互历史与候选模型编码成「历史-模型联合嵌入」,从日志轨迹学一个 outcome estimator 预测 turn 级效用,据此选模型。

结果

ScienceWorld 上超过 GPT-5 同时省 58.7%;HLE 上省 43.4%。且切换更少、对瞬时错误更容忍、模型间出现自发分工。

与你的想法:它在 Limitations 里明确讨论了切换导致的 prompt cache / KV 丢失,并靠"少切换、切换更稳"来缓解——但它把缓存丢失当成要规避的缺点,而不是像你那样把 decode↔cache-write 的价差当成要利用的套利信号。这正是分水岭。

TwinRouterBench — Static & Live Dynamic Eval for Agentic Routing

Pei Yang et al. (17 authors) · 2026 · arXiv 2605.18859
你们仓库用的数据集
背景

现有路由 benchmark 只测一次性 prompt、靠在线 LLM judge 评分,不反映长程 agent 的真实路由。

Motivation

做一个 step-level 路由 benchmark,用 execution-verified 目标 + 真实 API 花费,评估 coding agent / deep research 里的路由。

方法

双轨:static 轨(520 实例、970 个 router-visible prefix,SWE-bench/BFCL/mtRAG 等,确定性打分)+ dynamic 轨(SWE-bench Verified 实跑)。每个 LLM call 从锁定池选模型。

结果

提供一个可复现的 per-call 路由评测框架,测"官方任务解决率 + 实际 API spend"。你们本地那份轨迹成本分析正是基于此数据。

与你的想法:最接近的"桥"——per-call agent 路由 + 真实花费。存疑更正:论文摘要层面只提"realized API spend / token costs",未明写 fresh/cache-read/cache-write/output 四桶拆分($5/$0.5/$6.25/$25 四档是在你们本地数据/代码里体现的)。它没有把"预测 decode 量 / output-to-write 比值"当作路由信号。

Router-R1 — Multi-Round Routing & Aggregation via RL

Haozhen Zhang, Tao Feng, Jiaxuan You · NeurIPS 2025 · arXiv 2506.09033
多轮
背景

已有 router 多是"单轮、一对一"映射:一条 query 选一个模型,不能组合多个模型的能力。

Motivation

把多模型路由 + 聚合建模成序列决策过程,让 router 本身是个 LLM,交替"思考"与"调用模型"。

方法

RL 训练,规则化 reward(格式 + 结果 + 成本);只需模型的简单描述符(价格、延迟)即可泛化到没见过的模型。

结果

7 个 QA benchmark 上超过强基线,同时有效控制成本。

与你的想法:确实"多轮"、确实把回复并进上下文、确实带 cost reward——但它的"轮"是一个 QA 解答内部的协作子查询,不是面向环境的 agent turn,也不涉及缓存经济学。

TRIM — Targeted Stepwise Routing in Multi-Step Reasoning

Vansh Kapoor, Aviral Kumar et al. · ICLR 2026 · arXiv 2601.10245
机制同构
背景

多步推理易"级联崩溃":一步错则整解崩。现有路由把整条 query 交给一个模型,视所有步骤同等。

Motivation

只把"可能让解答脱轨的关键步"路由给大模型,常规续写留给小模型。

方法

每步弱模型先出候选,router policy 看部分推理链 + 候选,决定 accept(continue)或 escalate(大模型 regenerate);接受则把弱模型输出当状态留下。用 process reward + RL。

结果

在数学推理上以更低成本达到接近全强模型的准确率;把路由建模成"看 prefix 状态"的序列决策。

与你的想法:"弱模型出→接受则保留其输出"的机制几乎一模一样。差别:在数学推理链内做,优化 token/FLOPs,不涉及 API cache 经济学,不是 tool-using agent。

STEER — Confidence-Guided Stepwise Model Routing

Sangmook Lee et al. · AAAI 2026 · arXiv 2511.06190
轻量信号
背景

已有 router 训练外部 deferral 模块,跨域鲁棒性差,还要昂贵的 Monte Carlo rollout 造标签。

Motivation

不用任何外部模型,做 domain-agnostic 的 step 级路由。

方法

用小模型自己的 logit 置信度(生成每步前),经 Gaussian Mixture Model 校准,决定这步是否需要叫大模型。

结果

数学/多跳QA/规划上,AIME 上 +20% 准确率、省 48% FLOPs(vs 纯大模型),超过依赖外部模块的基线。

与你的想法:同为 reasoning-step 级、优化 FLOPs,非 agent loop、非 cache-aware。信号是"置信度",不是"成本价差"。

相关但更远的工作

方向相关,但要么是 query 级、要么侧重别的目标。含两个存疑待核实的引用。

Policy-Guided Stepwise Model Routing

2026 · arXiv 2605.06116
轨迹依赖视角
背景

step 级路由常被当成"每步孤立决策"。

Motivation

论证路由该看整条轨迹——当前步是否叫大模型,取决于 prefix 状态和之前的模型选择。

方法

把 stepwise 路由建成 policy over trajectory,而非局部难度判断。

结果

在成本-准确率上改进孤立决策基线。

与你的想法:"缓存状态(prefix + 历史模型选择)影响当前路由"这个轨迹依赖视角,和你"缓存状态该进路由目标"非常近——但它没把缓存的美元成本显式建模。

Agent-as-a-Router (ACRouter) — Agentic Routing for Coding

2026 · arXiv 2606.22902
coding agent
背景

coding agent 里模型选择的信息缺口大。

Motivation

用一个 agentic router 主动闭合"该用哪个模型"的信息缺口。

方法

Orchestrator + Verifier + Memory 三件套;配套 CodeRouterBench(~10K 实例、8 个 frontier LLM 的验证分)。

结果

在 in-distribution 任务上累积 regret 最低,并泛化到 OOD 编程任务。

与你的想法:确实是 agentic 路由,但按 regret / 能力 路由,不涉及 cache 经济学。
